- [x] **Retention purge job** — done 14 September. `services/retention.js` enforces the periods the owner approved (#10), as the LAST step of the nightly snapshot (through the same best-effort `step()` wrapper as every other source, so a failure records an error against `retention` in `source_sync`, marks the run partial and shows on the status page) and on demand as `npm run purge` (`scripts/purge-run.js`), for a first run or after a period is changed.
  - **What it deletes, and when.** AI briefings 12 months after they were generated; staff feedback 12 months after it was **reviewed or dismissed** — never while it is still `new`, because it is still waiting on a human; `snapshot_runs` and the `note` on each of those rows after 90 days, always keeping the single most recent run so the status page can still say when the data was last refreshed; the row-level `child_exits` detail after 2 years, while the `exits_monthly` counts it was folded into keep running for 7. The purge is stepped after the exit fold for exactly that reason: the night's departures become counts before the per-child rows are trimmed.
  - **What it must never touch.** Occupancy (`daily_metrics`, `ccs_payments`), wages (`labour_weekly`, `labour_budget`) and incident numbers (`incidents_monthly`) carry no personal data and are kept indefinitely — they are the history every trend is drawn from. They are not in the job's table list, and a test asserts they survive a purge.
  - **The periods live in one place**, as named constants in `services/retention.js` carrying the owner's decision and its date, each overridable by an environment variable so a period can be changed without a code change. Documented in `render.yaml`; a test fails if `render.yaml` and the constants disagree, or if a retention number appears in any other service.

    | Variable | Approved default | Covers |
    |---|---|---|
    | `RETAIN_AI_BRIEFINGS_MONTHS` | 12 | cached weekly AI briefings |
    | `RETAIN_FEEDBACK_MONTHS` | 12 | staff feedback, from the review — `new` is never deleted |
    | `RETAIN_RUN_LOG_DAYS` | 90 | `snapshot_runs` and their notes |
    | `RETAIN_EXIT_DETAIL_MONTHS` | 24 | `child_exits` row-level detail (2 years) |
    | `RETAIN_EXIT_AGGREGATE_MONTHS` | 84 | `exits_monthly` counts (7 years) |
    | `RETENTION_RECLAIM` | 1 | set to 0 only if the VACUUM that hands the freed pages back becomes too slow for the nightly run; the deletions happen either way |

    A value that is not a positive whole number is **ignored** and the approved default stands — `RETAIN_RUN_LOG_DAYS="ninety"` must never be read as "keep nothing".
  - **It never deletes a row it cannot prove is past its period.** Every clause runs the stored date through SQLite's `date()`, which returns NULL for anything it cannot parse, and compares the normalised value. A NULL, an empty string, prose, a half-padded `2015-9-4` — none is provably old, so all are KEPT; a shaped-but-impossible `2025-02-30` normalises *forward* to 2 March, so it errs the same way. A row somebody has to look at is a far smaller problem than a row deleted early. Feedback triaged before `feedback.reviewed_at` existed has no review date and is kept for the same reason.
  - **It reports counts, never content.** Per-table counts go to the log and to the `retention` row in `source_sync` (with the cutoffs in `meta_json`); what a deleted row said is never written anywhere — that would move the data rather than remove it. The deletions run in one transaction, and the freed pages are handed back with a WAL checkpoint and VACUUM so removed rows cannot be read out of the database file.
  - **Proof:** `tests/retention.test.js` — every period boundary pinned to a literal date with a row one day inside, one exactly on it and one outside; a `new` feedback row surviving a decade; the aggregate outliving the detail; the most recent run surviving any age; unparseable and impossible dates kept; occupancy, wages and incidents untouched; the log and `source_sync` carrying no content; a nonsense override ignored; idempotency; and the whole job, plus the CLI, running clean against an empty database.
  - **Sessions are the one table the job does not cover, and that is deliberate.** A row in `sessions` is personal information under APP 11 — it holds the signed-in user's id, email, name and role (never a password, never a child or family). It expires eight hours after that user's last request (now confirmed by the owner as the intended period), expired rows are refused on read, and the store deletes them every fifteen minutes and again at boot. Sweeping it a second time here would only give two things the chance to disagree, so `services/retention.js` records the period as `SESSION_HOURS` and a test asserts it still equals the store's own `MAX_AGE_MS`. A restore is a separate matter: the boot sweep removes only rows already past their expiry, so a backup younger than eight hours carries live sessions and restoring it would reinstate every login that was live when it was taken, including ones revoked since (logging out deletes the row but not the browser's cookie). `scripts/restore-db.js` therefore clears `sessions` on the restored file — a restore signs everyone out.

## Fixed in production, recorded so it is not rediscovered

- **Every write on the deployed site was refused** (14 September, `/admin/places`, `/ai/briefing`, every form). The browser was sending `Origin: null`, so the cross-origin guard treated the app's own forms as cross-site. The cause was this app's own `Referrer-Policy: no-referrer` header: Chrome ties the Origin header on a form submission to the page's referrer policy, and under `no-referrer` it strips it to an opaque origin. Reproduced in a real browser against a local copy, fixed by setting `Referrer-Policy: same-origin` — which still stops a dashboard URL (it can name a centre) reaching another site — and verified by submitting the form again. The guard itself was also made proxy-tolerant (hostname comparison against `req.hostname`, `Host`, `X-Forwarded-Host` and an optional `PUBLIC_HOSTNAME`), it now logs the values that disagreed, and a refusal renders an explanation with those values shown to admin and ops instead of the single word "Forbidden"

## Known data problems at source — not calculation faults

These limit what the dashboard can honestly show. Each page says so where it applies.

1. **Operating days compute to 253 in FY2026-27, not the CEO's 251.** Likely a Christmas closure that is not a public holiday. One line in `services/calendar.js` once confirmed.
2. **Four centres book above their licensed places**, so utilisation reads over 100% and unused places go negative. Either `centres.capacity` is not the licensed figure or the definition differs.
3. **Only 4 of 92 enrolled LineLeader records carry a start date**, so "started" counts in the funnel are a floor, not a total.
4. **No tour is ever marked complete or cancelled** in LineLeader, so "tours held" rests on the date having passed. A no-show nobody cancelled counts as held.
5. **LineLeader does not date offer acceptance**, so every current Offer Accepted member counts as an offer in the last 12 months. Bardia reads 94.7% offer rate because of a long-standing backlog.
6. **OWNA keeps booking rows on public holidays.** Seats, utilisation and average occupancy now exclude them; some older figures do not.
7. **Tours are matched to families by a hash of the family name within a centre**, as LineLeader gives no family id on the tour row. The name itself is no longer stored — both rows carry the same salted hash instead — but the limitation is unchanged: two families with the same name at one centre would be conflated. A family id on the LineLeader tour row would fix it properly.
